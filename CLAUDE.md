# TI4 Table

Browser sandbox for Twilight Imperium 4th Edition, for a private group of friends. No rules enforcement: players move tiles and pieces freely on a shared, real-time board. See README.md for usage.

This is one game on **All Hands On Board** (`../AllHandsOnBoard`), the platform that owns rooms, saving, history, rewind and checkpoints, the websocket and `useRoom`, the lobby, `HistoryPanel`, `FeedbackButton`, `/api/feedback` and all deployment. This repo publishes `@joeyanglx/ti4-rules` (`shared/`) and `@joeyanglx/ti4-client` (`client/`) to GitHub Packages, and the platform installs them; change infrastructure there, not here. The STS Table (`../STSBoardgame`) is the other game.

## Commands

- `npm run dev` — the `dev/` harness: the platform's server with only this game (:3001, `node --watch`, rooms in `dev/data/ti4/`) and its lobby on Vite (:5173, proxies `/ws` and `/api` to `PORT`), everything read from source (the `ahob-source` export condition). Platform packages come from GitHub Packages (`.npmrc`; `npm login --scope=@joeyanglx --auth-type=legacy --registry=https://npm.pkg.github.com` once)
- `npm run typecheck` — run after every change; there are no tests yet
- `npm run build` — builds both packages for publishing (`ahob-build` → `shared/dist`, `client/dist`); `npm run build -w dev && npm start` is a local production copy
- `npm run release -- <patch|minor|x.y.z>` — versions both packages together; pushing the printed `v*` tag runs the Publish workflow. Then the platform's `npm run update:games` and its deploy

## Architecture

npm workspaces, all TypeScript (ESM, strict):

- `shared/` (`@joeyanglx/ti4-rules`) — imported from source in this repo and from `dist/` once published. Hex math (axial, flat-top), piece kinds, `GameState`, `Action`, `applyAction`, map-string parsing, system data, and `ti4Rules` (`game.ts`, the platform's `GameRules`; new rooms start from `defaultBoard`). History records, `stateAt` and the protocol are the platform's (`@joeyanglx/ahob-core`).
- `dev/` (not published) — `server.mjs` (`startServer({ games: [ti4Rules] })`), `src/main.ts` (`mountPlatform` with only TI4) and a Vite config whose `gameAssets` serves `client/assets` at `/games/ti4/`. Feedback (`/api/feedback?game=ti4`) is the platform's: it writes `feedback.json` in the data folder, replies go in `feedback-replies.json`.
- `client/` (`@joeyanglx/ti4-client`) — React 19 + react-konva. `index.ts` exports `ti4Client` (`GameClient`); `Table.tsx` is the table, given the synced room by the platform as `TableProps`. Images are `client/assets/` (`factions/`, `tiles/`), served at `/games/ti4/`: build URLs with `ASSETS` (`client/src/assets.ts`); `Board` renders tiles/pieces; `Sidebar` holds the piece and system palettes; `TableBar` (over the map) holds the shared cards from `TablePanels` plus agendas and relics; `RightPanel` holds your player board (`CardsPanel`), the `Overview` (with the discard pile) and history.

## Conventions

- **Every board change is an `Action`** handled in `applyAction` (`shared/src/state.ts`), which must stay pure. The client applies actions optimistically, the server applies the same function and relays to the other clients. Never mutate state outside it.
- **Card, strategy, seat, planet, battle and round actions are server-ordered** (`isServerOrdered`): clients don't apply them optimistically, the server echoes them to everyone including the sender, so concurrent draws and clamped counters can't diverge. Player economy, planet cards and promissory notes live in `shared/src/players.ts` (a note is only recorded in `state.promissory` once it leaves its owner's hand), command/speaker token moves between panel and map in `shared/src/tokens.ts`, dice rolls (results are rolled client-side and carried in the action) in `shared/src/dice.ts`, and battles in `shared/src/battle.ts` (one `state.battle` at a time; it works on a snapshot of the system's stacks and only writes back to `state.pieces` on `battle/end` with `apply`; ground combat has a `planet`, and with `landing` the attacker's ground forces in the system's space join and are put on the planet on apply; a space battle with `cannonOnly` is space cannon offense from a side with no ships in the system — `spaceCannonsAt` in `shared/src/spaceCannon.ts` — so only the attacker rolls space cannon, once, with no rounds or swap; and a piece is on a planet when it's inside that planet's circle — `planetAt` in `shared/src/planets.ts`, using the `x`/`y`/`radius` on each planet in systems.json) (the speaker is either `state.speaker` or a single `speaker` piece on the map); read seats through `seatOf` so older seats get defaults. Several names can share a colour, so a piece's owner is the seat with that colour that picked a faction (`pieceUnitStats` in `shared/src/unitStats.ts`). Adjacency for space cannon is touching hexes plus matching wormholes (`adjacentSystems` in `shared/src/adjacency.ts`); hyperlanes aren't followed. Free rolls from the top-bar dice are `dice/roll` with kind `free` and never count as hits. `round/end` is the status phase in one action (ready planets and technologies, clear command tokens from the board, return strategy cards and passes). Randomness goes in the action as a `seed` (`seededRandom`), never `Math.random` inside `applyAction`.
- **History and rewind** (`shared/src/history.ts`, the platform's server): the server records every action with a description from `describeAction` (written from the state before the action; keep hidden cards out of it) and replays from the latest checkpoint to rewind. An action whose `applyAction` returns the same state object is refused: not recorded or sent. That only works because actions are deterministic: never read the clock or `Math.random` in `applyAction`; put seeds, dice results and new ids in the action. A new action type needs a `describeAction` case.
- Hands (`state.cards.hands`) are keyed by player name and sent to everyone; the UI just hides other players' cards. `withDefaults` (`shared/src/setup.ts`) fills in fields missing from older saved rooms (and keeps an in-progress `battle`) — extend it when adding top-level state.
- New features usually mean: add an `Action` variant → handle it in `applyAction` → dispatch it from the UI. The server needs no change.
- Board coordinates are in "board pixels" (`HEX_SIZE` = 100, hex centre to corner). Tiles are keyed by `hexKey(q, r)`; pieces have free x/y.
- Map strings follow the TTS / map generator format: ring by ring, starting from the top hex and going clockwise (`hexRing`).
- System data (`shared/src/data/systems.json`) and tile images (`client/assets/tiles/ST_<id>.webp`) were generated from the KeeganW/ti4 repo, official tiles only (base, PoK, Thunder's Edge). Don't hand-edit the JSON in bulk; regenerate it.
- Card data (`shared/src/data/cards.json`) is generated by `scripts/import-cards.mjs` from the AsyncTI4 bot repo. Card ids are AsyncTI4 aliases, unique per copy (`sabo1`..`sabo4`); agendas, relics and technologies are prefixed `agenda_`/`relic_`/`tech_` to avoid clashes. Deck contents per edition (`base` / `pok` / `te`), including playable factions, live in its `editions` field. Faction icons (`client/public/factions/<alias>.webp`) come from `scripts/import-faction-icons.py`. Factions carry `startingFleet` and `homeSystems` (tile ids) for `homeSetup` (`shared/src/homeSetup.ts`); those two fields were added to the current cards.json from the bot's factions/*.json without a full regeneration.
- `crypto.randomUUID` is unavailable over plain http on a LAN IP — use `newId()` in `client/src/id.ts`.
- Pieces are placeholder circles with labels (`PIECE_STYLE`); real unit art hasn't been added yet. Neutral pieces (speaker, custodians) have fixed colours in `NEUTRAL_PIECES`; a new game and loading a map put the custodians token on Mecatol Rex (`withCustodians`).
- Deploying: release the packages, then in the platform `npm run update:games`, push and `sudo ahob-update` on the server (rooms and an in-progress battle survive the restart). Deployment scripts live only in the platform.
- Style: 2-space indent, single quotes, small focused components, comments only where the "why" isn't obvious.
